# Cравнение протоколов и сервисов для live-данных

## Решения:

1. **Base OData query** - обычный способ запросить данные через OData.

2. **OData track-changes / delta** - способ после первого чтения получать только изменения.

3. **Microsoft Graph Delta Query** - delta-подход для данных Microsoft Graph.

4. **Base GraphQL query** - клиент сам указывает, какие данные ему нужны.

5. **GraphQL subscription** - клиент подписывается на события, а сервер присылает их при изменениях.

6. **GraphQL Live Query** - сервер поддерживает результат запроса актуальным и присылает обновления.

7. **Google Cloud Firestore** - база данных, где можно подписаться на запрос и получать изменения в реальном времени.

8. **RethinkDB changefeeds** - поток изменений из базы по интересующим данным.

9. **HTTP conditional GET over OData** - клиент проверяет, изменились ли данные, и загружает их заново только при необходимости.

10. **Meteor Livequery with MongoDB** - Meteor следит за результатом запроса к MongoDB и обновляет данные на клиенте.

## Таблица 2. Изменения и восстановление

| Решение | За чем следим | Что сообщает сервер | Как приходят изменения | Переход от чтения к слежению | После обрыва | Если история слишком старая |
|---|---|---|---|---|---|---|
| **1. Base OData query** | За изменениями не следит. | Отдельных событий об изменениях нет. | Клиент узнаёт новое состояние только после повторного запроса. | Отдельной подписки нет, поэтому переход не нужен. | Нужно просто выполнить запрос заново. | История изменений не хранится. |
| **2. OData track-changes / delta** | За изменениями в отфильтрованной коллекции. | Сервер сообщает, какие элементы изменились, появились или были удалены из результата. | Клиент периодически запрашивает только изменения. | В исходной таблице не указана отдельная гарантия, что между первым чтением и началом отслеживания ничего не потеряется. | Можно продолжить синхронизацию по `deltaLink`. | Старый `deltaLink` может стать недействительным, тогда потребуется начать заново. |
| **3. Microsoft Graph Delta Query** | За изменениями всей коллекции для тех ресурсов, где эта возможность есть. | Сервер возвращает новое состояние объекта или отметку о его удалении. | Клиент запрашивает изменения по delta-механизму; уведомление может дополнительно сообщить, что появились новые данные. | Переход между первым чтением и дальнейшим отслеживанием должен согласовать клиент. | Можно продолжить с сохранённого `deltaLink` и восстановить актуальное состояние. | Сервер может признать старый маркер недействительным и потребовать новую синхронизацию. |
| **4. Base GraphQL query** | За изменениями не следит. | Отдельных событий нет. | Чтобы увидеть новое состояние, запрос нужно выполнить снова. | Отдельной подписки нет. | Нужно повторить запрос. | История изменений не хранится. |
| **5. GraphQL subscription** | За потоком событий, который определяет приложение. | Сервер отправляет изменение данных или другое событие, заданное приложением. | События приходят от сервера по активной подписке. | Между обычным запросом начальных данных и запуском подписки может быть промежуток, в котором изменение потеряется. | Сам стандарт не даёт способ получить все пропущенные события. | История событий обычно не хранится самим механизмом подписки. |
| **6. GraphQL Live Query** | За результатом конкретного запроса. | Сервер присылает обновлённый результат целиком или только изменившуюся часть. | Обновления приходят от сервера автоматически. | Для клиента начальный результат и дальнейшие обновления связаны одной схемой работы, но полная серверная гарантия отсутствия потерь в исходном файле не заявлена. | После переподключения можно снова получить актуальный результат. Пропущенная история отдельно не восстанавливается. | История изменений не хранится. |
| **7. Google Cloud Firestore** | За результатом конкретного запроса. | Сервер сообщает, что документ появился, исчез или изменил положение в результате. | Обновления приходят от сервера автоматически. | Клиент может продолжить отслеживание с позиции, полученной до первого чтения. | Можно продолжить по сохранённому маркеру и получить актуальное состояние. | Сервер может потребовать полный перезапуск отслеживания. |
| **8. RethinkDB changefeeds** | За диапазоном ключей или ограниченным отсортированным результатом. | Сервер сообщает об изменении строки, а для ограниченного отсортированного списка — ещё и об изменении её позиции. | Изменения читаются через одно долго живущее соединение. | Начальные данные и дальнейшие изменения выдаются одной операцией. При этом исходный файл отдельно не утверждает полную гарантию отсутствия потерь. | Встроенного механизма получения всех пропущенных событий нет. | История изменений не хранится. |
| **9. HTTP conditional GET over OData** | Не следит за отдельными изменениями. | Сервер только сообщает, изменилась ли ранее полученная версия данных. | Клиент периодически перепроверяет ресурс. | Подписки нет, поэтому переход не нужен. | Нужно снова проверить или получить ресурс. | История изменений не хранится. |
| **10. Meteor Livequery with MongoDB** | За результатом конкретного запроса. | Сервер сообщает, что элемент появился, исчез или изменился. | Обновления приходят от сервера автоматически. | Начальный результат и дальнейшее отслеживание связаны без отдельного промежутка между двумя запросами. | После переподключения результат строится заново. Полная история изменений не проигрывается. | Сам Livequery историю не хранит; на уровне MongoDB есть отдельный журнал с ограниченным сроком хранения. |

## Таблица 3. Как клиент узнаёт о возможностях

| Решение | Может ли клиент сам узнать о дополнительных функциях | Как он это узнаёт | Что делать, если функции нет |
|---|---|---|---|
| **1. Base OData query** | Да. OData позволяет серверу описывать свои возможности в стандартном виде. | Клиент читает `$metadata`. | Ничего менять не нужно: обычный OData-запрос и есть базовый вариант. |
| **2. OData track-changes / delta** | Да, если сервер сообщает о поддержке отслеживания изменений. | Информация может быть указана в `$metadata`, а ответ сервера показывает, был ли режим применён. | Можно отказаться от delta-механизма и просто повторять обычные запросы. |
| **3. Microsoft Graph Delta Query** | Частично. Саму функцию `delta` можно обнаружить, но её ограничения зависят от конкретного ресурса. | Часть информации видна в описании API, а детали обычно приходится знать из документации Microsoft Graph. | Можно использовать обычные постраничные запросы без отслеживания изменений. |
| **4. Base GraphQL query** | Клиент может узнать структуру схемы, но не все особенности поведения сервера. | Через introspection GraphQL можно посмотреть доступные типы и поля. | Обычный GraphQL-запрос уже является базовым вариантом. |
| **5. GraphQL subscription** | Клиент может увидеть, что в схеме есть подписки, но стандарт не описывает все их гарантии. | Через GraphQL-схему видно `subscriptionType`; способ передачи зависит от используемого транспорта. | Можно выполнять обычные запросы и периодически повторять их. |
| **6. GraphQL Live Query** | Это зависит от конкретной реализации. Единого стандарта для Live Query нет. | В схеме может быть видна директива `live`, но по одному её наличию нельзя узнать все детали поведения. | Можно выполнять обычный GraphQL-запрос и периодически обновлять его. |
| **7. Google Cloud Firestore** | Нет универсального механизма, который позволил бы любому клиенту заранее узнать все такие возможности. | Обычно клиент уже знает Firestore API и SDK. Некоторые ограничения обнаруживаются по ошибке запроса. | Можно сделать обычный разовый запрос без подписки. |
| **8. RethinkDB changefeeds** | Частично. Некоторые свойства становятся понятны уже после выполнения запроса. | По типу ответа или по ошибке можно понять, поддерживается ли нужная форма changefeed. | Можно выполнить обычный запрос без отслеживания изменений. |
| **9. HTTP conditional GET over OData** | Частично. Клиент может увидеть, что сервер возвращает маркер версии ресурса. | Например, по заголовку `ETag` в ответе. | Можно выполнять обычный GET без проверки версии. |
| **10. Meteor Livequery with MongoDB** | Нет универсального способа автоматически обнаружить Livequery. Клиент должен заранее знать, что работает с Meteor. | Это определяется знанием протокола и конфигурации приложения, а не общим описанием возможностей. | Внутри самого Livequery отдельного универсального базового режима нет. |
