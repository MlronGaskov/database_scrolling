
# Спецификация событий, версий и восстановления

## Назначение

ISTREAM предназначен для синхронизации отдельных материализованных диапазонов упорядоченного результата запроса без необходимости поддерживать весь результат на клиенте.

В рассмотренных подходах не выявлен единый механизм, одновременно обеспечивающий частичную начальную загрузку, range-scoped delta, replay изменений и локальное восстановление диапазона при недоступной истории событий.

## Модель событий

Изменения результата запроса описываются четырьмя логическими операциями.

| Операция | Условие | Данные | Действие клиента |
|---|---|---|---|
| **insert** | Строка появилась в результате или вошла в диапазон | `id`, `newKey`, `row` | Добавить строку по `newKey` |
| **update** | Значения строки изменились, но ключ порядка остался прежним | `id`, `key`, `row` | Обновить значения строки |
| **delete** | Строка удалена, перестала удовлетворять запросу или вышла из диапазона | `id`, `oldKey` | Удалить строку по `oldKey` |
| **move** | Строка осталась в результате, но изменила ключ порядка | `id`, `oldKey`, `newKey`, `row` | Удалить строку по старому ключу и добавить по новому |

Здесь `id` соответствует стабильному $rowId(r)$, `key` - полному ключу порядка $K_Q(r)$, а `row` содержит пользовательские значения $Value_Q(r)$.

`move` является логической операцией, а не обязательным типом события протокола. Она может передаваться как `delete(oldKey)` и `insert(newKey)` с одинаковым `rowId` в одной версии. Отдельный wire-тип `move` допускается как оптимизация.

Изменение `rowId` рассматривается как удаление одной строки и добавление другой.

## Версионирование

Каждой атомарно применяемой группе изменений соответствует монотонно возрастающая логическая версия $v$ - позиция в журнале изменений.

Для события $e$ определяется $version(e)=v$.

Все изменения одной атомарной группы имеют одинаковую версию и применяются клиентом как единое целое.

Каждый материализованный фрагмент $f_i=(I_i,Rows_i,v_i)$ хранит собственную версию $v_i$, до которой применены все релевантные изменения.

Разные фрагменты могут находиться на разных версиях. Поэтому глобальная уникальность `rowId` в произвольном состоянии клиента не требуется.

Для каждого фрагмента клиент хранит `appliedVersion`, соответствующий последней полностью применённой версии $v_i$. Повторно полученные изменения с версией не больше `appliedVersion` не применяются.

## Начальное получение диапазона

Клиент запрашивает выбранный диапазон $I$ результата запроса $Q$:

`FetchRange(Q, I)`

Сервер возвращает:
- `rows` - все строки диапазона;
- `asOfVersion = v` - версию согласованного серверного состояния.

Полученные строки соответствуют эталонному фрагменту $F(Q,I,v)$.

Клиент создаёт материализованный фрагмент $f_i=(I,Rows_i,v)$.

Начальное получение одного диапазона не требует загрузки всего результата запроса или остальных диапазонов.

## Переход от чтения к подписке (fetch → watch)

После получения диапазона клиент открывает поток изменений:

`Watch(Q, I, afterVersion = v)`

Сервер должен передать все релевантные изменения с версиями больше $v$, включая изменения, произошедшие между завершением `FetchRange` и открытием `Watch`.

Для этого используется журнал изменений. Переход считается корректным, если сервер может воспроизвести все релевантные изменения после версии начального чтения.

Если необходимая история уже недоступна, сервер возвращает `history-expired`. Клиент повторно получает диапазон и открывает подписку с новой версии.

Таким образом, между начальным чтением и подпиской не возникает пропуска изменений.

## Range-scoped delta

Для каждого материализованного диапазона $I$ сервер формирует только изменения, влияющие на его содержимое.

Изменение релевантно диапазону, если старый или новый ключ строки принадлежит $I$.

| Старый ключ | Новый ключ | Изменение диапазона |
|---|---|---|
| Вне $I$ | Внутри $I$ | `insert` |
| Внутри $I$ | Вне $I$ | `delete` |
| Внутри $I$ | Внутри $I$ | `update` или `move` |
| Вне $I$ | Вне $I$ | Событие не передаётся |

Если строка отсутствует в результате $Q$ до или после изменения, соответствующий старый или новый ключ считается отсутствующим.

При неизменном ключе передаётся `update` только при изменении пользовательских значений. При изменении ключа используется `delete` + `insert` либо эквивалентный `move`.

Сервер передаёт изменения одной версии для диапазона одной атомарной группой:

`delta(rangeId, version, operations)`

где:
- `rangeId` - идентификатор отслеживаемого диапазона;
- `version` - версия атомарной группы;
- `operations` - все релевантные операции этой версии для диапазона.

Клиент применяет группу атомарно и обновляет `appliedVersion` после успешного применения.

События передаются в порядке версий. Пропуски номеров версий допустимы, если соответствующие изменения не затрагивают диапазон.

## Stream watermark

Логическая версия события и stream watermark являются разными понятиями.

**Stream watermark** $V$ подтверждает, что сервер передал все изменения с версиями не больше $V$, релевантные отслеживаемому диапазону.

Для подтверждения прогресса сервер отправляет сообщение:

`progress(rangeId, watermark = V)`

Это сообщение передаётся после всех релевантных событий с версиями не больше $V$ и может отправляться даже при отсутствии изменений в диапазоне.

Клиент после применения всех предшествующих изменений может установить `appliedVersion = V`.

Получение `progress` без применения предшествующих событий не означает достижения версии $V$.

Watermark относится к конкретному потоку диапазона. Разные фрагменты клиента могут иметь разные подтверждённые версии.

## Replay после разрыва

После потери соединения клиент сохраняет материализованные диапазоны и их последние полностью применённые версии.

Для восстановления фрагмента $f_i$ клиент открывает подписку:

`Watch(Q, I_i, afterVersion = v_i)`

Если история доступна, сервер передаёт все релевантные изменения с версиями из интервала $(v_i,V]$ в порядке версий.

Клиент:
1. применяет полученные группы изменений атомарно;
2. игнорирует уже применённые версии;
3. обновляет `appliedVersion`;
4. после сообщения `progress` подтверждает актуализацию фрагмента до $V$.

Replay не требует повторного получения диапазона и не затрагивает остальные материализованные фрагменты.

## Недоступная история событий

История изменений хранится ограниченное время. Сервер определяет минимальную версию, начиная с которой возможно полное воспроизведение последующих изменений.

Если клиентская версия слишком старая для replay, сервер возвращает:

`history-expired(rangeId)`

В этом случае клиент:

1. прекращает подписку для соответствующего диапазона;
2. помечает его текущее состояние как требующее восстановления;
3. повторно получает только этот диапазон через `FetchRange(Q, I_i)`;
4. заменяет старые строки новым состоянием и принимает новый `asOfVersion`;
5. открывает `Watch` начиная с новой версии.

Если история вновь недоступна при открытии подписки, процедура повторяется.

Остальные материализованные диапазоны сохраняют своё состояние и продолжают синхронизацию независимо.

## Нормализация и проверка

Для эталонной проверки используется операция $Normalize(C_Q,V)$, приводящая проверяемые фрагменты к общей версии $V$.

Для каждого фрагмента:
- если replay доступен, применяются изменения из $(v_i,V]$;
- если replay недоступен, выполняется повторное получение диапазона из состояния $D_V$;
- при replay достижение $V$ подтверждается сообщением `progress`.

После нормализации каждый проверяемый фрагмент имеет вид $(I_i,Rows_i^V,V)$.

Корректность состояния проверяется сравнением с $F(Q,I_i,V)$, включая состав строк, значения, порядок и глобальную уникальность `rowId`.

В обычной работе нормализация всех фрагментов к одной версии не требуется.
